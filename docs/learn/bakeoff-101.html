Course 1 · The question

Why build the same harness twice?

Rocket Agent v2's loop will run inside the RocketRide engine: one Python 3.12 process, one event loop, and a fixed set of installed packages. Two ways to write it were on the table:

A · pydantic-ai library
A framework runs the loop for you: Agent.iter() calls the model, runs tools, keeps history, retries, asks for approvals. You write the glue.
B · our own loop hand-written
About 870 lines on raw httpx: we write the request, read the stream, run the tools. Some tricky pieces are ported from Pi, an MIT-licensed coding agent.

Arguing about which is better goes nowhere, so the repo builds both and measures. Click a question to see how the repo answers it.

The answer shapeThe repo never names a winner. It collects evidence for each side (the README's "Where each wins", the report's last section), and people decide.
Course 1 · The question

A fair fight: everything is shared except the loop

If each version had its own tools, storage and tests, you couldn't tell whether a difference came from the loop or from everything else. So the repo draws one line, the seam, and shares everything below it. Only the two loop folders are counted.

OS linkA child process gets its own memory, so the only ways the parent learns what it did are its stdout/stderr (through a pipe), its exit code, and the files it wrote. That's exactly how the driver judges it: the child prints one JSON line, and the truth is read from log.sqlite. An exit code of −9 means "killed by signal 9", which is SIGKILL.

Course 2 · On the machine

Inside the process: one event loop juggles several tasks

The engine runs Python's asyncio, so the harness must too. One OS thread runs an event loop; each concurrent job is a task that pauses at every await. Below is step 1 of scenario S02, drawn from the real event timestamps (t_us, microseconds since the turn started). Toggle between the loops.

real timestamps
OS linkEverything here is concurrency, not parallelism: one core, switching between tasks while each waits on the network or disk. That's why a tool can "start while the model is still streaming": the stream reader is waiting for the next bytes anyway. The GIL would stop threads from helping; see why the benchmark puts the fake server in its own process (Course 9).

Course 3 · On the network

One step is one HTTP POST, answered as a stream of events

A model has no memory between calls. Each step, the loop POSTs the whole conversation as JSON to /chat/completions, and the server answers with SSE: lines starting with data:, each carrying one small delta. These are the real bytes the fake server sent for step 1 of S02. Step through them and watch what the loop's Stream object accumulates.

Network linkThe response is one HTTP/1.1 response with chunked transfer encoding: the server doesn't know the length up front, so it sends pieces as the model produces them. fakeprov/server.py writes each piece as b"%x\r\n%s\r\n" (hex length, bytes), and 0\r\n\r\n to end. It also turns off Nagle's algorithm so tiny frames leave at once.
In the codeB reads lines with resp.aiter_lines() and does one json.loads per data: line (our_version/loop.py lines 184–223, Course 6). A never sees these bytes: the OpenAI SDK parses them and pydantic-ai turns them into PartDeltaEvents (Course 7).
Course 3 · On the network

Opening a connection costs round trips; reusing one is free

Before the first byte of a request, a new connection needs a TCP handshake, and on https:// also a TLS handshake: two or three round trips, around 100 ms to a far-away server. Keep-alive lets the next request reuse the open connection. The fake server stamps each request with the connection that carried it; here are S02's seven requests.

Course 3 · On the network

The fake model server: a script, a cursor and a recorder

fakeprov is a small HTTP server from Python's standard library (ThreadingHTTPServer: one OS thread per connection). It never thinks; it plays back a scenario's scripted answers in order. The URL tells it which script, which run and which loop is asking, so A and B each get their own cursor over the same script.

Why a fakeA real model answers differently every time and costs money. Course 5 · The shared harness

The session log: one SQLite file, and history can only grow

Every conversation lives in one SQLite file: threads (one row per conversation, with its frozen system prompt and model settings minus the API key), turns, items and events. Triggers make items and events append-only: the database itself refuses to change or delete them.

Starting tools early, and running reads side by side

A tool call streams in pieces: {"na, me": "tool_, pipe"}. B counts braces as pieces arrive, and when a read-only call's arguments parse as a complete object it may start that call before the model has finished talking. Two rules keep this safe:

  • Order: a call starts early only if every call before it did, so a read never runs ahead of an earlier write.
  • Permission: only if check() says allow now, and never on the last allowed step (its results could never be sent).

Course 8 · Proving it works

Crashing on purpose: SIGKILL at an exact moment

Scenario S08 has the driver start a child process (bakeoff turn) with a special event sink. The moment the runner publishes the tool result's item (so it's already safely in SQLite), the sink kills its own process with SIGKILL: no cleanup, no finally blocks, like a power cut. Then the driver runs bakeoff resume in the parent.

src/bakeoff/shared/scenario.pylines 179–199
179def crash_sink(event_type: str, call_id: str | None = None) -> Sink:180    """A sink that SIGKILLs this process at the first published event of `event_type` (about181    `call_id`, if given; see fakeprov/README.md, "Crash points"). The runner publishes an `item`,182    `tool.start` or `turn.end` only after storing it, so the crash comes right after it is183    durable and before the loop can run again."""184 185    def sink(envelope: dict[str, Any]) -> None:186        if envelope["type"] != event_type:187            return188        data = envelope["data"]189        if call_id is not None:190            about = (191                data["item"]["message"].get("tool_call_id")192                if event_type == "item"193                else data.get("call_id")194            )195            if about != call_id:196                return197        os.kill(os.getpid(), signal.SIGKILL)198 199    return sink

OS linkSIGKILL can't be caught or ignored: the kernel removes the process. What survives is only what was already on disk, which is exactly what the harness relies on. The real child here was PID 2758710 and exited with −9. The fake server, in the parent process, kept running, so the resumed turn continues the same scripted conversation.

Course 9 · Measuring it

Counting lines of code honestly

metrics/loc.py reads each file with Python's own tokenizer and gives every physical line exactly one kind: code, docstring, comment or blank. Only code is the headline number, so a loop can't look bigger or smaller by commenting more. A file that starts with # Ported from … is counted apart.

Per file, code lines. ported files are from Pi. measured on main.
Reading the numbersB has more code (869 vs 778), but 468 of B's lines are ported: they came with years of other people's fixes, so they're mostly reading, not writing. A has fewer lines, but after one real turn, 216,554 lines of third-party code have been loaded to run it (next screen), against 18,592 for B. Both facts are true; which one matters more is the decision.

Course 9 · Measuring it

Does it fit in the engine? One environment, one version of each package

The engine is one Python environment, so every package can exist in exactly one version, and every node's requirements must agree. A resolver (here uv pip compile) either finds versions that satisfy everyone or reports a conflict. Pick a pydantic-ai version:

In the codescripts/engine_fit.sh writes the engine's binding requirements (crewai>=1.14.1,<2, which needs openai<3; pydantic==2.12.5; httpx==0.28.1) plus each loop's dependencies into one file and asks uv to resolve it. CI runs it on every pull request. That's why A is pinned to 2.31.1 in pyproject.toml, while CI also runs all tests against the latest pydantic-ai.
Course 9 · Measuring it

Harness overhead: time the loop adds on top of the model

The model's own time isn't the loop's fault, so the benchmark removes it. Each measured turn streams 2,000 chunks and a tool call from the local fake server with zero delay. Then a bare httpx client sends the same request bodies and just reads the lines: the baseline. Loop time minus baseline time is what the harness itself costs: parsing, events, request building, tool dispatch.

measured, 100 turns per loop
OS linkThe fake server runs in its own process for the benchmark. In a thread of the same process it would compete with the loop for the GIL; on this laptop that made every frame 3–4× slower for both and added noise (metrics/bench.py docstring). Each loop is also benchmarked in a fresh subprocess, so its memory numbers aren't polluted by the other.
Keep it in proportionA real model takes 1–7 seconds per step (the live runs, next screen). 370 ms per turn is noticeable; 13 ms isn't. And since the live runs' time per step was within 10% on chat completions, the model dominated there.

The evidence on each side, and what it doesn't say

After ten courses, this is what the measurements support. A timing only counts as a win if it's at least 10% better; live results only over two or more runs of the same setup.

B · our loop wins on
  • Installs less: 12 packages, 3.9 MB (A: 35, 35.4 MB)
  • Starts faster: 71.4 ms cold import (A: 1.19 s)
  • Adds less per turn: 12.8 ms (A: 369.8 ms), memory +3.3 MB (A: +67.4 MB)
  • Starts read tools while streaming: 20 early starts (A: 0)
  • Reuses connections: 29 for 59 requests (A: 56)
  • Fits the engine at any version: it needs only packages the engine ships
  • Never re-encodes a message it already sent, which prompt caches need
A · pydantic-ai wins on
  • Less code of its own: 778 lines (B: 869, 468 of them ported)
  • New APIs mostly come with the library: Responses API +97 lines (B: +156)
  • Retries, limits, approvals, cancellation and history format are maintained upstream
  • One interface to many providers (Anthropic, Gemini…), if the engine ever needs them
  • Library-validated tool arguments with its own retry prompt
Too close to call
Scenarios: 22/22 each. Live runs: all 10 built and validated chat.pipe. On chat completions, time per step (1.49 vs 1.60 s) and tokens per step are within 10%. On the Responses API, B's 6.31 s vs 7.19 s per step is based on only 2 runs each, with the model doing most of the work: treat it as a hint.
What it doesn't sayNothing here measures the rest of Rocket Agent v2 (sessions for many users, storage, UI streaming, app building). This compares only the loop and its provider layer. The decision also weighs things the repo can't measure: who maintains the code, and how fast the library moves.
